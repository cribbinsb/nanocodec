Browser (WebAssembly)

The nc-web crate compiles our encoders and decoders to WebAssembly with wasm-bindgen. The demo runs on this module; so can your page. Every codec the native build has is in it.

Build the module

rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.105 --locked
tools/web/build.sh        # writes web/pkg/, web/pkg/relaxed/ and web/pkg/scalar/

Each directory holds nc_web.js (an ES module) and nc_web_bg.wasm. The three builds give bit-identical output: pkg/ uses SIMD128, pkg/relaxed/ adds relaxed SIMD, and pkg/scalar/ uses no SIMD at all (the scalar reference kernels). web/wasm.js picks the relaxed build where WebAssembly.validate accepts a relaxed-SIMD probe, else the SIMD128 build where it accepts a SIMD128 probe, else the scalar one.

Browser support

  • Any engine with WebAssembly runs it; SIMD128 makes it fast. Chrome and Edge 91, Firefox 89 and Safari 16.4 were the first versions with SIMD128; an older engine gets the scalar build, which decodes 720p about 4-6 times slower (H.264 4.9x, AV1 3.7x, VP9 6.4x per frame, node 22, 2026-11-27), and the demo says so on the page. Relaxed SIMD: current Chrome and Firefox validate it, Safari does not (it gets the SIMD128 build).
  • Tested engines (tools/web/browser_engines.py, Playwright's headless builds on Linux, 2026-11-27): Chromium 148, Firefox 150 and WebKit 26.4 (Safari's engine) each decode the official conformance corpora with the build wasm.js picks there, and run the demo end to end, except 10-bit VVC in WebKit (203 of 221 VVC streams wrong: its optimizing JIT miscompiles one SIMD128 intra kernel; not fixed yet); Chromium without SIMD runs the scalar build through both. Not tested: Safari itself on macOS or iOS (WebKit's Linux port uses other media back ends), mobile browsers, and the webcam in WebKit (Playwright's Linux WebKit refuses camera access). Results: docs/results/browser-engines-2026-11-27/.
  • The browser encoder accepts sizes from 64x64 to 1920x1080 and up to 60 fps. Encoding and decoding are single-threaded per instance; the demo runs each encoder and decoder in its own Web Worker.

The JavaScript API

  • await init(), the module's default export, loads and instantiates the WebAssembly file next to nc_web.js. A page that starts several workers can compile the module once and pass the WebAssembly.Module to each, as web/wasm.js does (init({ module_or_path })).
  • new SourceFrame(width, height) holds an input frame; fill it with from_rgba(rgba) (canvas pixels) or from_planes(...) (a WebCodecs VideoFrame's YUV planes).
  • new BrowserEncoder(codec, width, height, qp, fps, keyInterval, preset, overrides, filmGrain, colour, stillCamera, spatialLayers) creates a fixed-QP encoder (overrides, colour, stillCamera and spatialLayers may be undefined; the preset is a rung of the ladder); set_rate_control(targetKbps, peakKbps, bufferMs) switches it to real-time rate control. encode(source) (or encode_at(source, timestampUs) for a live source) returns the packet as a Uint8Array; repeat is true when nothing was coded. request_keyframe() asks for a key frame.
  • new BrowserDecoder(codec); decode_frame(packet, index, references) returns an outcome (decoded, or the freeze reason). rgba_frame(colour) and i420_frame() return an offset into memory.buffer where the picture is.
  • A call into the module may grow its memory, which detaches earlier views of memory.buffer: take the offset first, then make the view and copy from it at once.

Minimal standalone page

Draws a moving picture on a canvas, encodes it with H.264 at 300 kbps, decodes every packet and draws the decoded picture beside the source. It loads the demo's module from ../../pkg/: run it here. To use it elsewhere, copy it next to a pkg/ directory from the build and change the import path; serve it over HTTP, as browsers do not load modules from file:// pages.
